# 68000 frontend (`components/m68kjit`)

A dynarec for the Motorola 68000 built **on top of the emulator's own Musashi
interpreter**, not beside it. mame-go (Neo Geo, CPS1, 68000 arcade boards) and
gwenesis (Mega Drive) both run Musashi; the dynarec translates blocks of 68000
code into Xtensa code that works on Musashi's registers, flags and cycle counter,
and calls Musashi's own opcode handler for any instruction it does not translate.
So every instruction works from the first day, and the result is the
interpreter's, instruction by instruction.

## The block

A block is a run of instructions from one PC, in fixed code (ROM) only: code in
RAM is interpreted, so no write can make a block stale. It ends after an
instruction that never falls through (BRA, JMP, JSR, BSR, RTS, RTE, TRAP, ...) or
at 64 instructions. Per instruction the generated code does what the
interpreter's loop body does, with the fetch and decode done once:

    PPC = pc; PC = pc + 2; IR = op; handler(); cycles -= cyc[op];
    if (PC != next || cycles <= 0) leave;

A block leaves exactly where `m68k_execute()` would stop or change course: a
taken branch, an exception, an interrupt taken inside a memory handler (mame-go's
Musashi 3.1 takes it immediately), or the end of the time slice.

## Native instructions

Instructions the translator knows become Xtensa code that updates Musashi's state
itself: no call, no PPC/IR stores for register-only forms, and the flag bits
Musashi's handlers produce (X/C in bit 8, N/V in bit 7, Z = 0 when set; the other
bits are don't-care and differ between Musashi's 32- and 64-bit builds).

| Group | Forms |
|---|---|
| Moves | MOVEQ; MOVE/MOVEA between registers, `#imm` and every memory mode (`(An)`, `(An)+`, `-(An)`, `(d16,An)`, `(d8,An,Xn)`, abs.w/.l, `(d16,PC)`, `(d8,PC,Xn)`); MOVEM (register list unrolled) |
| Arithmetic / logic | ADD SUB CMP AND OR from registers, `#imm` or memory; EOR Dn,Dm; ADDA SUBA CMPA; ADDQ SUBQ; ORI ANDI SUBI ADDI EORI CMPI; the read-modify-write forms (`Dn,<mem>`, ADDQ/SUBQ and the immediates on memory) |
| Other | TST, CLR (register and memory), SWAP, EXT.w/.l, LEA and PEA on every control mode; LSL LSR ASL ASR ROL ROR by `#n` on Dn |
| Flow | Bcc and DBcc (conditions from the flags, the CPU type's not-taken cycles), BSR, JSR, RTS |

Left to their handlers, on purpose: BRA and JMP (Musashi's branch-to-self idle
rule differs between versions), the rest of the instruction set (MULU/DIVU,
ADDX/SUBX, BCD, bit operations, shifts by a register count and on memory,
ROXL/ROXR, MOVE to/from SR/CCR/USP, TRAP, RTE, ...). In random valid 68000 code,
84 % of the executed instructions are native.

Memory goes through the interpreter's own accessors (address mask, function
code), in Musashi's order (source before destination, reads before writes), with
PC holding what the interpreter's REG_PC holds at each access. Two Musashi
version quirks are host settings: `MOVE.l`/`MOVEM.l` to `-(An)` as two 16-bit
writes (Musashi 4.x) and the per-CPU cycle adjustments (not-taken branches,
DBcc, shift counts, MOVEM registers).

## Chaining

An exit with a known target (a taken Bcc/DBcc, the fall-through at the end of a
block, BRA/BSR) jumps through a slot: at first the slot holds a stub that returns
to the dispatcher and records the slot; once the dispatcher has the block at that
target, the slot holds the block's chain entry and the exit goes straight there.
The cycle check stays in front of every chained jump, so a chained run stops
where `m68k_execute()` stops. On random code this removes a third of the returns
to the dispatcher; loops (DBcc, Bcc back) chain to themselves.

## The emulator side

`m68kjit.h`: the emulator fills an `m68kjit_host_t` from a small glue file
compiled against its own Musashi (see `test/m68k-test/main/glue_musashi.c` for
Musashi 4.5) and calls `glue_jit_execute()` in place of `m68k_execute()`: the same
function with its loop body handed to `m68kjit_run()`. mame-go and gwenesis get
their own glue for their Musashi version.

## Verification

![How every change is verified](img/verify.svg)

`test/m68k-test` (see its README):

1. **Lengths**: `m68kjit_insn_len()` equal to Musashi's disassembler on all 45799
   opcodes valid on the 68000 (PC).
2. **Block model**: the C form of the blocks against `m68k_execute()` on random
   machines, with four mutations the fuzz must catch (PC).
3. **Generated code**: the same fuzz in QEMU with the Xtensa backend: 300 seeds
   of random valid code, 300 seeds whose ROM is 85 % natively translated forms,
   and 20 seeds for each of the 23 instruction families alone, compared after each
   of 32 time slices with random interrupt levels (registers, SR, USP/ISP, cycles
   used and left, RAM hash). Registers start at edge values half the time, and in
   the native passes `MOVE SR,-(A7)` after half the instructions puts their flags
   into the RAM hash. Every native group
   was also broken on purpose once (a wrong V on ADD, the not-taken cycles, the
   A7 byte step, the index sign extension, the chain's cycle check, ASL's V) and
   the fuzz caught each; it also found one real bug on the way (the PC store
   clobbered the value of a memory-to-memory MOVE).
